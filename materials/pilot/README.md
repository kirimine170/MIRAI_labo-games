# パイロット教材パック

## 目的

このパックは，完成済みの `sword-clicker` と `robot-repair-clicker` を使い，学習者が次のサイクルを45分で経験するための授業試行版である．

> 観察 → 再現 → 仮説 → 修正 → 検証 → 説明

正解コードを早く当てることではなく，症状と原因を区別し，根拠のある修正を行い，修正後もゲームの規則が保たれていることを確かめる力を扱う．

## 対象と前提

- 主対象は，小学校高学年から中学生のScratch経験者である．
- 変数，条件分岐，イベントまたはメッセージ送信の基本を既習とする．
- 1人1台または2人1台で実施する．2人の場合も，各自が説明欄を記入する．
- 欠陥のない完成版と，教師が準備した欠陥版を使う．本パックは欠陥候補の仕様だけを定め，ゲームコード自体は変更しない．
- 本家Scratchでの動作確認を正式な確認とし，TurboWarpだけの成功を完成条件にしない．

## ファイル構成

| ファイル | 用途 | 主な利用者 |
|---|---|---|
| `lesson-plan-45min.md` | 45分の進行，時間配分，授業目標 | 教師 |
| `student-worksheet.md` | 観察から説明までの記録用紙 | 生徒 |
| `teacher-guide.md` | 事前準備，介入，別解判定，LLM利用，安全配慮 | 教師 |
| `hints.md` | 課題別の段階ヒント | 教師・生徒 |
| `rubric.md` | 7観点，0〜3点の評価基準 | 教師・生徒 |
| `defect-candidates.md` | 欠陥注入仕様と問題なし課題 | 教材開発者・教師 |
| `qa-checklist.md` | 配布前，実施中，実施後の品質確認 | 教材開発者・教師 |

## 標準課題セット

| 課題ID | ゲーム | 中心概念 | 観察できる症状 |
|---|---|---|---|
| `SW-B01` | sword-clicker | 境界条件 | HPが0でも最初の敵を倒せない |
| `SW-S01` | sword-clicker | 状態管理 | クリア表示後にゲームオーバーへ変わる |
| `RR-F01` | robot-repair-clicker | フィードバック不足 | 数値は増えるが途中の外見が変わらない |
| `NB-R01` | robot-repair-clicker | 問題なしの判断 | 仕様とテスト結果に不一致がない |

1回の授業では原則1課題を割り当てる．初回は `SW-B01`，次に `RR-F01`，転移確認に `SW-S01`，過剰修正を測る場面で `NB-R01` を使うことを想定する．課題IDと版の対応は生徒へ知らせず，「問題がない可能性がある」とだけ伝える．

## 成功条件

教材の成功は，学習者がコードを変更したかどうかだけでは判断しない．次を満たせば，問題なし課題で変更しない判断も成功とする．

1. 期待する動作と実際の動作を区別して記録した．
2. 他者が追試できる再現手順を作った．
3. 症状に関係する変数，条件，イベントの流れを根拠に仮説を立てた．
4. 修正した場合は，変更と仮説の関係を説明した．
5. 正常系，境界値，回帰の観点で検証した．
6. 問題が見つからない場合は，調べた範囲と「変更しない」理由を説明した．

## 運用上の注意

- 生徒へ `defect-candidates.md` の注入箇所と教師用判定情報を配布しない．
- ヒントは一度に答えまで示さず，`hints.md` の段階を一つずつ開示する．
- 速さやヒント使用回数だけで成績を下げない．何を確かめて理解を更新したかを評価する．
- 氏名，顔，声，メールアドレス，チャット全文を標準ログに含めない．詳細は `teacher-guide.md` に従う．
- LLMの提案を採用した場合も，学習者本人が原因，変更，テスト結果を説明する．説明できない修正は完了とみなさない．
