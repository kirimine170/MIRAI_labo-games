# 欠陥候補と問題なし課題

## 取扱区分

この文書は教材開発者・教師用である．欠陥注入箇所と期待解答を，課題実施前に生徒へ配布しない．ここに示す変更は候補仕様であり，リポジトリ内の既存ゲームコードには適用していない．

各欠陥版は完成版の複製から一候補だけを注入し，版ID，元コミット，変更差分を記録する．数値を好みで調整する課題ではなく，値，条件，状態，イベントの関係を追えることを優先する．

## 共通の準備・受入条件

- 意図した症状が，記載した手順で3回中3回再現する．
- 意図した欠陥以外では，開始，操作，UI，成功，失敗，再挑戦が完成版と一致する．
- 構文エラーや起動不能を欠陥として使わない．
- 修正前後を同じ操作で比較できる．
- 本家Scratchと対象端末で確認する．
- ファイル名や課題名から欠陥分類が推測できない配布方法を使う．

## `SW-B01` HPが0という境界を扱えない

### 教材上の狙い

「0より小さい」と「0以下」の違いを暗記するのではなく，クリック可能条件と撃破条件を同じ値の表で比較し，どちらにも含まれない状態ができる理由を説明する．

### 注入仕様

- 基準ゲーム：`games/sword-clicker`
- 対象：`main.gs` の `onclick` 内
- 完成版の条件：`if current_hp <= 0`
- 欠陥候補：撃破イベントの条件を，`current_hp < 0` の時だけ成立するようにする．
- それ以外の行は変更しない．

### 生徒へ示す固有仕様

- スライムのHPが0になったクリックで，倒した数が1増え，次のスライムが出る．
- HPが0のスライムへ，追加のクリックを要求しない．

### 再現手順と症状

1. 緑の旗を押し，ゲーム開始を待つ．
2. 最初のスライムを5回クリックする．
3. HP表示が0で止まり，倒した数が増えず，追加クリックも受け付けないことを確認する．

`onclick` の外側には `current_hp > 0` というクリック可能条件があるため，0へ到達した後にもう一度クリックして負数にすることもできない．0が二つの条件の隙間になる．

### 修正の受入テスト

| テスト | 期待結果 |
|---|---|
| 4回クリック | 最初のスライムのHPが1で，倒した数は0 |
| 5回目をクリック | HPが0へ到達した同じクリックで，倒した数が1になる |
| 3体を必要回数クリック | 3体目でクリアし，余分な4体目は出ない |
| クリックせず時間切れ | ゲームオーバーになる |
| 終了後にクリック | 進行値が変わらない |

### 妥当な別解

完成版と同じ `<= 0` への修正が最小案である．HPを減らした直後に `== 0` を判定する案も，現在の1クリック1減少という仕様の下では受け入れられる．ただし，将来1回に複数ダメージとなり0を飛び越える場合の違いを説明させる．外側のクリック条件を変えて負数までクリック可能にするだけの案は，HP0で撃破する仕様を満たさないため受け入れない．

## `SW-S01` クリア後もプレイ中の状態が続く

### 教材上の狙い

見えているクリア画面と，内部の `game_state` が同じ意味で終端状態になっているかを区別する．状態を変えないと，別の時間処理が後から結果を書き換える因果関係を追う．

### 注入仕様

- 基準ゲーム：`games/sword-clicker`
- 対象：`stage.gs` の `finish_game_clear`
- 欠陥候補：`game_state = "clear"` による終端状態への更新を行わない．
- クリア表示，スライム非表示，UI非表示の処理は残す．

### 生徒へ示す固有仕様

- 3体目を倒すとクリアし，緑の旗を押すまで結果は変わらない．
- クリア後は，制限時間の処理やクリックによる進行が止まる．

### 再現手順と症状

1. 3体を時間内に倒す．
2. クリア表示が出ても，緑の旗を押さずに待つ．
3. 残り時間に相当する秒数の後，ゲームオーバー表示へ変わることを確認する．

スライムとUIが隠れるため，一見すると終了している．しかし，`game_state` が `playing` のままなので，1秒ごとの処理は時間を減らし続ける．

### 修正の受入テスト

| テスト | 期待結果 |
|---|---|
| 3体目を倒す | クリア表示になる |
| クリア後15秒以上待つ | クリア表示が維持され，ゲームオーバーにならない |
| 時間切れまで倒さない | ゲームオーバーになる |
| 終了後にクリック | HP，撃破数，結果が変わらない |
| 緑の旗で再挑戦 | `intro` から始まり，最初の値へ戻る |

### 妥当な別解

`finish_game_clear` の冒頭で `game_state` を `clear` にする案が最小である．タイマー停止用の別状態や明示的な終了フラグを追加する案も，共通受入条件を満たし，状態遷移を説明できれば受け入れる．タイマー処理だけを削除する案はゲームオーバーの規則を壊すため受け入れない．クリア後にゲームオーバー表示を隠すだけの案も，内部処理が継続する原因を解消しないため不十分である．

## `RR-F01` 進行を外見へ通知しない

### 教材上の狙い

内部値が正しいことと，利用者へ結果が伝わることを分ける．イベントを介した送信側と受信側を追い，操作に対する段階的フィードバックがゲーム理解へ必要な理由を考える．

### 注入仕様

- 基準ゲーム：`games/robot-repair-clicker`
- 対象：`stage.gs` の `add_repair_progress`
- 欠陥候補：進行更新後の `broadcast "robot_progress_update"` を送らない．
- 修理数，パーセント，クリア判定，完了時の `robot_complete` は残す．

### 生徒へ示す固有仕様

- クリックすると，修理数とパーセントが増える．
- 修理率が25％以上，50％以上，75％以上，100％へ初めて到達した時，ロボットの外見が対応する段階へ変わる．
- 30回で100％となり，クリアする．

### 再現手順と症状

1. 緑の旗を押し，ゲーム開始を待つ．
2. 8回，15回，23回の時点で，修理数，パーセント，外見を記録する．
3. 数値は増えるが，ロボットが0％の外見のままであることを確認する．
4. 30回目では，完了イベントによって初めて100％の外見になることを確認する．

パーセントは `floor` により整数へ切り下げられる．30分の8は26％，15は50％，23は76％となるため，最初の到達クリックは8，15，23，30回である．

### 修正の受入テスト

| クリック数 | パーセント表示 | 外見 | その他 |
|---:|---:|---|---|
| 0 | 0％ | `robot_0` | プレイ開始 |
| 7 | 23％ | `robot_0` | まだ25％未満 |
| 8 | 26％ | `robot_25` | 最初の25％以上 |
| 15 | 50％ | `robot_50` | |
| 23 | 76％ | `robot_75` | 最初の75％以上 |
| 30 | 100％ | `robot_100` | クリアする |

追加で，時間切れ時にゲームオーバーとなり，緑の旗で0％へ戻ることを確認する．

### 妥当な別解

進行値更新後に `robot_progress_update` を送る完成版の方法が最小である．`stage.gs` から外見更新を直接呼ぶ構造へ再設計する案も，スプライト間の責務と動作互換性を説明でき，すべてのテストを通れば受け入れられる．各クリック数へ個別のコスチューム変更を直書きする案は，パーセント境界との重複と保守性を説明させた上で判断する．100％だけ外見を変える案は途中の仕様を満たさない．

## `NB-R01` 問題なしの完成版

### 教材上の狙い

「必ずバグがある」という前提でコードを変える過剰修正を避け，仕様に基づく検証から，変更しない判断を説明する．異常の有無と，好みの難易度改善を区別する．

### 配布仕様

- 基準ゲーム：変更していない `games/robot-repair-clicker`
- 欠陥注入：なし
- 他の課題と同じ配布形式，ファイル名，説明量にする．

### 生徒へ示す固有仕様

`RR-F01` と同じ仕様を示す．加えて，次を示す．

- 制限時間内に30回クリックするとクリアする．
- 時間切れではゲームオーバーとなる．
- 終了後は結果が変わらず，緑の旗で最初から再挑戦できる．
- 仕様との不一致がなければ，コードを変更せずに報告してよい．

### 合格となる証拠

- `RR-F01` のクリック境界表を実測し，表示と外見が一致する．
- クリア経路とゲームオーバー経路をそれぞれ確認する．
- クリア後とゲームオーバー後に待ち，結果が変わらないことを確認する．
- 緑の旗による初期化を確認する．
- 「30回は多い」などの好みは改善提案へ分ける．
- 調べた範囲と限界を述べ，「すべてのバグが存在しない」ではなく，「提示仕様に対する不一致を確認できなかった」と結論づける．

### 不要な変更の扱い

学習者が `max_repair`，`time_limit`，コスチューム境界を変更しても，直ちに失敗とはしない．元へ戻して仕様テストをやり直し，なぜ欠陥修正ではなかったか説明できれば，学習の証拠として扱う．変更を残す場合は，欠陥修正ではなく改善版として別保存する．

## 別解をレビューする共通質問

1. その変更は，どの観察事実に対応するか．
2. 変更前に立てた仮説と一致するか．
3. 境界の直前，ちょうど，直後でどうなるか．
4. 開始，成功，失敗，再挑戦を壊していないか．
5. 症状を隠しただけで，内部の原因が残っていないか．
6. 次に設定値が変わっても成立するか．
7. 学習者本人が，LLMや教師の説明なしで因果関係を話せるか．
